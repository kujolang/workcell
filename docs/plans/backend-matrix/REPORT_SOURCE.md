# Backend matrix research source ledger

Research date: 2026-09-01  
Scope: WorkCell architecture, provider APIs, execution substrates, security boundaries, cost surfaces, and distribution paths  
Evidence rule: first-party documentation establishes documented behavior, not independent proof of a provider's isolation implementation. Unknowns remain `null` in `BACKEND_MATRIX.json`.

## Canonical research conclusion

WorkCell should keep one small adapter protocol while representing provider and substrate as separate receipt identities. Docker and Podman are direct adapters. Hosted sandboxes are external provider adapters. gVisor and Kata are substrate selections beneath an adapter. Raw Firecracker is deliberately excluded until an operator supplies provisioning, guest transport, evidence, inventory, and ownership-safe destruction.

The initial implementation batch is Docker, Podman, E2B, Vercel Sandbox, and Daytona. This is an architecture-coverage choice, not a general-purpose provider quality ranking. It preserves the existing contract, proves two local engine implementations, and adds three materially different remote control planes without requiring a generic scheduler.

## Claim-to-source ledger

| Decision-driving claim | First-party evidence | Architectural use |
|---|---|---|
| Docker exposes resource, PID, network, mount, log, and lifecycle controls through an engine API/CLI. | [Docker run reference](https://docs.docker.com/engine/containers/run/), [resource constraints](https://docs.docker.com/engine/containers/resource_constraints/), [network drivers](https://docs.docker.com/engine/network/drivers/) | Built-in adapter and v1 compatibility baseline. |
| Podman has a Docker-compatible CLI shape but different rootless networking and runtime resolution. | [Podman run](https://docs.podman.io/en/latest/markdown/podman-run.1.html), [rootless tutorial](https://github.com/containers/podman/blob/main/docs/tutorials/rootless_tutorial.md) | Separate built-in adapter sharing OCI helpers; never backend-name conditionals in core. |
| E2B exposes sandbox create/connect, command streaming, filesystem transfer, timeout, and lifecycle APIs. | [E2B SDK reference](https://e2b.dev/docs/sdk-reference/js-sdk/v2.15.2/sandbox), [commands](https://e2b.dev/docs/commands), [filesystem](https://e2b.dev/docs/filesystem) | First remote adapter and disposable sandbox vertical slice. |
| Vercel Sandbox exposes a public REST API, command execution, files, network policy, snapshots, and explicit stop semantics. | [Vercel Sandbox REST API](https://vercel.com/docs/rest-api/reference/endpoints/sandbox), [Sandbox](https://vercel.com/docs/vercel-sandbox), [network policy](https://vercel.com/docs/vercel-sandbox/concepts/networking), [snapshots](https://vercel.com/docs/vercel-sandbox/concepts/snapshots) | Second remote adapter; proves REST transport and ephemeral/persistent resolution. |
| Daytona exposes sandbox lifecycle, process execution, file transfer, Git, resource selection, and self-hosted deployment. | [Daytona API](https://www.daytona.io/docs/en/api/), [sandbox lifecycle](https://www.daytona.io/docs/en/sandboxes/), [self-hosted installation](https://www.daytona.io/docs/en/installation/) | Third remote adapter; proves operator-controlled deployment and tier-aware capability negotiation. |
| Modal Sandboxes are remote containers with command, filesystem, timeout, snapshot, and network controls, but the supported integration is SDK-centered. | [Modal Sandboxes](https://modal.com/docs/guide/sandbox), [network access](https://modal.com/docs/guide/sandbox-network-access), [snapshots](https://modal.com/docs/guide/memory-snapshot) | Official adapter after the first batch; validates the external runtime-shim strategy. |
| Cloudflare Sandbox runs through Workers, Durable Objects, and Containers and has platform request and lifecycle limits. | [Cloudflare Sandbox](https://developers.cloudflare.com/sandbox/), [limits](https://developers.cloudflare.com/sandbox/platform/limits/), [security](https://developers.cloudflare.com/sandbox/platform/security/) | Later operator bridge after the 1.0 compatibility surface stabilizes. |
| Runloop exposes devbox lifecycle, command execution, file transfer, and snapshots/checkpoints. | [Runloop devboxes](https://docs.runloop.ai/devboxes/overview), [commands](https://docs.runloop.ai/devboxes/commands), [snapshots](https://docs.runloop.ai/devboxes/snapshots) | Later official agent-sandbox adapter. |
| Fly Machines are low-level remotely managed VMs with lifecycle and volume APIs rather than a bounded single-run sandbox contract. | [Machines API](https://fly.io/docs/machines/api/), [Machine lifecycle](https://fly.io/docs/machines/machine-states/), [volumes](https://fly.io/docs/volumes/) | Community/operator adapter; WorkCell must add its own guest transport and evidence plane. |
| Firecracker supplies a microVM VMM and API, not a complete remote execution service. | [Firecracker design](https://github.com/firecracker-microvm/firecracker/blob/main/docs/design.md), [API specification](https://github.com/firecracker-microvm/firecracker/blob/main/src/firecracker/swagger/firecracker.yaml) | Deliberately unsupported as a direct backend. |
| Kata Containers and gVisor integrate below an OCI/Kubernetes execution surface. | [Kata architecture](https://katacontainers.io/docs/architecture/), [gVisor architecture](https://gvisor.dev/docs/architecture_guide/), [gVisor Docker quick start](https://gvisor.dev/docs/user_guide/quick_start/docker/) | Receipt-visible substrate profiles, not provider adapters. |
| Kubernetes Jobs, Nomad, Fargate, Cloud Run Jobs, and Azure Container Apps Jobs schedule attempts and services with retry/control-plane semantics beyond a single WorkCell attempt. | [Kubernetes Jobs](https://kubernetes.io/docs/concepts/workloads/controllers/job/), [Nomad jobs](https://developer.hashicorp.com/nomad/docs/job-specification), [AWS Fargate](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/AWS_Fargate.html), [Cloud Run Jobs](https://cloud.google.com/run/docs/create-jobs), [Azure Container Apps Jobs](https://learn.microsoft.com/azure/container-apps/jobs) | Later external orchestrator adapters only; Dispatch continues to own workflow retries. |
| Wasmtime/WASI exposes a different workload and capability ABI from the existing container workload contract. | [Wasmtime WASI](https://docs.wasmtime.dev/wasi.html), [component model](https://component-model.bytecodealliance.org/) | Separate future execution mode, not a transparent backend. |

## Verification limits

No billable provider environments or private credentials were used. API-level conformance, isolation claims, maximum runtime, regional availability, quotas, pricing, resource telemetry, and cleanup behavior must be revalidated against the exact adapter version and target account before release. Provider-reported cost and usage are evidence inputs; WorkCell does not estimate unknown costs.
